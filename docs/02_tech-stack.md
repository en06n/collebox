# 技術選定

この文書は移行後の設計方針を記す。現行実装は Next.js + TypeScript / Drizzle。システム構成と機能範囲は [アーキテクチャ](04_architecture.md) と [機能仕様](01_features.md) を参照。

## 採用方針

| 領域 | 採用技術 | 選定理由 |
|---|---|---|
| フロントエンド | React + TypeScript + Vite | 一覧・フォーム・絞り込みの UI を React で構築し、TypeScript で画面や API のデータ型を開発時に検査する。ログイン後の操作が中心なので、Vite で SPA をビルドし、静的に配信できる。リクエストの実行時検証は Go API が担う。 |
| バックエンド | Go REST API | CRUD・検索・認可を単一の API にまとめる。標準ライブラリを起点に必要な依存だけを追加でき、単一バイナリとして配布しやすい。API とフロントエンドを別々にデプロイ・拡張できる。 |
| データベース | Supabase PostgreSQL | グッズと所有者の関係、所持数などを制約とトランザクションで整合させられる。検索条件に合わせて SQL とインデックスを調整できる。Supabase のマネージド DB を使い、DB サーバーの運用を減らす。 |
| 認証 | Supabase Auth | ログイン、セッション、アクセストークンの発行を任せる。Go API はトークンを検証し、グッズや画像のアクセスを認可する。 |
| 画像保存 | Cloudflare R2 | 画像本体をオブジェクトストレージに置き、DB には識別子を保存する。S3 互換 API を利用でき、画像の容量と配信を DB から独立して管理できる。 |

## 候補・未確定事項

| 領域 | 候補 | 判断基準 |
|---|---|---|
| HTTP ルーティング | Go 標準の `net/http` または chi | ルート構成や認証ミドルウェアの共通化に必要な機能で判断する。 |
| DB アクセス | pgx / pgxpool + sqlc | PostgreSQL ドライバと接続プールを使い、SQL から型付き Go コードを生成する案。Supabase の接続モードと prepared statement の互換性も確認する。 |
| コンテナ | Docker | ローカルとデプロイ先で同じ API イメージを利用する案。 |
| フロント配信 | Vercel または Cloudflare Pages | Vite の静的成果物の配信、SPA のルーティング、プラン条件を比較する。 |
| API 配信 | Google Cloud Run | コンテナの自動スケールを利用できる。無料枠を超えた利用は課金されるため、デプロイ前にリージョン、課金方式、通信・イメージ保管などの関連費用を確認し、予算通知と最大インスタンス数を検討する。予算通知は支出の上限ではない。 |
| CI/CD | GitHub Actions | フロントと Go のテスト・ビルドを自動化し、デプロイの自動化範囲は配信先の決定後に詰める。 |
| API 契約 | OpenAPI | リクエスト・レスポンスとエラーを共有する案。型やクライアントの生成を使うかは未定。 |

ログイン方式、DB の接続モード、R2 へのアップロード方式、テスト・整形ツールの選定は実装時に詰める。

## 負荷が増えたときの方針

API の応答時間、遅い SQL、DB 接続数を測る。一覧はページングし、所有者と実際の検索条件に合わせてインデックスを見直す。API を水平に増やすと各インスタンスの DB 接続も増えるため、最大インスタンス数 × プールの接続上限に運用用の余裕を加え、DB 側の接続予算に収める。

- [Supabase の接続方式](https://supabase.com/docs/guides/database/connecting-to-postgres)
- [Cloud Run の料金](https://cloud.google.com/run/pricing)
